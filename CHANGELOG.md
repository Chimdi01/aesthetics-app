# Changelog / build history

Chronological log of what's been built and why, in the order it happened.
This is the detailed rationale trail — **CLAUDE.md stays focused on
current-state reference material** (stack, conventions, environment
gotchas, how to work with the person) and points here for the "why did we
end up here" history. If you're trying to understand the current shape of
a feature, start in CLAUDE.md; come here when you need the backstory
behind a specific decision.

- Done: project skeleton, DB connection, `User` model, `ProviderProfile` model (1:1 with `User`, `role=provider`), `UserCreate`/`UserPublic`/`ProviderProfileCreate`/`ProviderProfilePublic` schemas, `POST`/`GET` endpoints for both, JWT auth (`POST /auth/login`, `get_current_user`/`get_current_provider` dependencies protecting provider-profile creation), Alembic migrations (initial schema migration applied, `create_all` removed from app startup). Confirmed running locally end-to-end.
- Also done: `ProviderProfile.categories` (multi-select `ServiceCategory` array — see Conventions) so multi-specialty providers (e.g. hair + makeup) don't need special-casing. `Booking` model/schemas/router (`POST /bookings/`, `GET /bookings/{id}`, `GET /bookings/as-customer`, `GET /bookings/as-provider`, `PATCH /bookings/{id}/status`) — customer ↔ `ProviderProfile`, category (must be one the provider offers), shop-visit vs. house-call (address required for the latter), status state machine (`requested → confirmed → completed`, `cancelled` from either non-terminal state; confirm/complete are provider-only, cancel is either party). Price/transport_fee are optional nullable fields for now (no per-service pricing catalog yet — see the categories-vs-Service-model tradeoff noted above).
- Also done: `Review` model/schema/routes — `POST /bookings/{booking_id}/review` (customer-only, requires the booking to be `completed`, one review per booking — enforced by a unique constraint on `booking_id` plus an application-level check) and `GET /providers/{profile_id}/reviews` (public listing, newest first). `provider_profile_id` is denormalized onto `Review` (copied from the booking at creation time) so listing/aggregating a provider's reviews doesn't need a join through `Booking` — same tradeoff already made for `Booking.category`. Rating is constrained to 1–5 both in the Pydantic schema (`Field(ge=1, le=5)`, returns 422) and as a DB `CheckConstraint` (defense in depth, in case a row is ever inserted outside the API).
- Also done (security hardening pass on reviews): `ReviewCreate.comment` rejects embedded null bytes via a Pydantic `field_validator` — Postgres rejects `\x00` in text columns at the driver level, which would otherwise surface as an unhandled 500 instead of a clean 422. `GET /providers/{profile_id}/reviews` takes `limit` (default 20, max 100) / `offset` query params — an unbounded SELECT there would let a provider with a large review history turn every page load into an ever-growing query.
- Also done: portfolio photo/video upload — `PortfolioMedia` model, `POST /providers/me/portfolio` (multipart upload, provider-only), `GET /providers/{profile_id}/portfolio` (public, paginated), `DELETE /providers/me/portfolio/{media_id}` (owner-only). Storage is local disk for now (`app/storage.py`, path from `settings.media_root`, served via `StaticFiles` mounted at `/media` in `app/main.py`) — **explicitly a placeholder**: local disk doesn't survive a redeploy on most hosting platforms and won't scale past one server, so this gets swapped for S3 before a real launch (the person building this has confirmed that's the plan). Everything that knows *where* files physically live is isolated in `app/storage.py`; routers/models only ever see the relative path it returns, specifically so that swap later touches one file, not the model/schema/router layer. Security hardening already applied here since it was built with the "avoid Sonar/Checkmarx-flagged issues" standard in mind from the start: content-type allowlist (rejects anything not image/jpeg, image/png, image/webp, video/mp4, video/quicktime), on-disk filenames are always server-generated (never the client-supplied filename, to block path traversal), upload size is capped while streaming chunk-by-chunk rather than trusting `Content-Length`, and `delete_file` refuses to unlink anything outside `media_root` even though the path it receives is always self-generated (defense in depth).
- Also done: location-based provider search — `ProviderProfile.location` (PostGIS `Geography(POINT, 4326)` via the new **GeoAlchemy2** dependency, nullable — providers without a location just don't appear in search) and `address_type` (`shop`/`home`, required whenever a location is given, per the roadmap). `GET /providers/search?latitude&longitude&radius_km&category&limit&offset` (public; radius default 10 / max 50 km, results sorted by distance with an id tiebreaker, includes `average_rating`/`review_count` from a grouped reviews subquery). **Privacy decision:** neither the profile response nor search results expose exact coordinates — a home provider's coordinates are effectively their home address — only `address_type` and a distance rounded to 0.1 km. Revisit (e.g. a coarsened point) if a map view needs pins. The GiST spatial index is created by GeoAlchemy2 itself when the column is added (an explicit `create_index` in the migration is a duplicate and fails). Test DB setup now runs `CREATE EXTENSION IF NOT EXISTS postgis` in `tests/conftest.py`.
- Also done: provider availability/working hours — `ProviderAvailability` model (`day_of_week` + `start_time`/`end_time`, one row per shift), `PUT /providers/me/availability` (provider-only, **full-replacement** semantics — deletes the provider's existing week and inserts the new one in the same request, rather than a per-day PATCH, since "set my working hours" is naturally one coherent action) and `GET /providers/{profile_id}/availability` (public, sorted Monday-first then by start time). **Split shifts are supported** (e.g. 09:00-12:00 and 14:00-18:00 on the same day) — multiple rows per day are allowed, but overlapping ranges on the same day are rejected in `ProviderAvailabilityUpdate` (`app/schemas/provider_availability.py`), not the DB: a single-row `CheckConstraint` can enforce `end_time > start_time` but can't compare across rows, so cross-range overlap has to be an application-level check. Booking creation deliberately does **not** validate against this table — providers already manually accept/decline every request, so an odd-hours booking just gets declined rather than blocked at request time; revisit only if usage shows it's needed. Times are timezone-naive wall-clock (fine for a single-city London launch, would need revisiting for multi-timezone expansion).
- Also done: in-app messaging — `Message` model, `POST /bookings/{booking_id}/messages` and `GET /bookings/{booking_id}/messages` (both in `app/routers/bookings.py`, reusing the booking-ownership check, not a new router — messaging is scoped to a Booking's back-and-forth, not a general DM system between arbitrary users, per the roadmap's V1 wording). Either party (customer or provider on that booking) can read/send; `_authorize_booking_party()` was factored out of the previously-duplicated is_customer/is_provider check (now shared by `get_booking`, `update_booking_status`, and both message endpoints). **Push notifications are explicitly NOT built** — that needs a push provider (FCM/APNs) and device-token registration, an external-account decision like Stripe, deferred for the same reason (no account/credentials to wire up yet). This just persists/retrieves messages.
- **Scaling posture (prompted by an explicit "millions of users, high concurrency" requirement):** the stance taken is "build the cheap, hard-to-retrofit foundations now; defer the expensive, premature infrastructure until real traffic justifies it" — see the Conventions entry on indexing and the gotcha on `CONCURRENTLY` migrations in CLAUDE.md. Concretely added: composite indexes on every FK/filter column an existing query actually uses (see that Convention entry), `db_pool_size`/`db_max_overflow`/`db_pool_timeout` made configurable in `app/config.py` (defaults are dev-appropriate, NOT scaled up blindly — real tuning is a per-deployment exercise, see the comment there), and `pool_pre_ping=True` on the engine (detects a stale pooled connection before handing it to a request, cheap insurance that matters more as connection churn grows). **Deliberately NOT done yet** (would be premature optimization pre-launch, and contradicts this project's own scope-discipline conventions): caching layer (Redis), read replicas, message queues/background workers, sharding, a CDN, multi-region. These are real V-next concerns once there's actual traffic data to size them against — worth raising in the architecture/roadmap conversation as a distinct "scaling milestones" discussion (e.g. "add read replicas when X", "add a queue when Y") rather than building speculatively now.
- Also done: application-wide logging — `app/logging_config.py` (`configure_logging()`, called once at import time in `app/main.py`) sets up the root logger via `logging.config.dictConfig`; every module just does `logger = logging.getLogger(__name__)` and logs normally, no per-module handler setup. `LOG_LEVEL` env var controls the level (default INFO). A per-request correlation id (`app/request_context.py`'s `request_id_var`, a `contextvars.ContextVar` — not a plain global, since it must stay correct across concurrently in-flight requests on one event loop) is set by a middleware in `app/main.py`, injected into every log line via `RequestIdFilter`, and echoed back as an `X-Request-ID` response header (reusing a caller-supplied one if present, for tracing across future hops like a load balancer). **Log-level policy, chosen specifically to stay sane at real traffic volume** (this was an explicit ask: "millions of users... concerned about how much logging will be done once there's even a little traffic"): the request-logging middleware logs by *outcome*, not by path — successful requests (2xx/3xx) are DEBUG, not INFO, because meaningful business events (booking created, review posted, login, profile/availability/portfolio changes) already get a purpose-built INFO log with real context from whichever router handled them; a generic "METHOD /path -> 200" line for every single request (every search, every profile view, every health-check poll) would otherwise dominate production logs without adding information. 4xx -> WARNING and 5xx -> ERROR regardless of path, since errors are actionable regardless of volume. Unhandled exceptions are caught in the middleware and logged via `logger.exception` (full traceback + request id) before re-raising, so nothing fails silently with only whatever uvicorn prints to stderr. **Never logged, anywhere**: passwords, raw JWTs/Authorization headers, user-generated message/review body content (not even at DEBUG — only metadata like sender id), or exact search/location coordinates above DEBUG (a home provider's or searching customer's coordinates are effectively a home address).
- Also done: `GET /health` (liveness — no dependency checks, must stay cheap since an orchestrator restarts the *process* on repeated failures here, which doesn't help if the database is what's actually down) and `GET /health/ready` (readiness — pings Postgres via `SELECT 1`, returns 503 if unreachable; a load balancer/orchestrator should route traffic away from an instance that's alive-but-not-ready rather than let it serve errors). Both endpoints' own successful responses are DEBUG-level under the log policy above, same as any other 2xx. A `/metrics` (Prometheus-style) endpoint and a build/version endpoint were considered and deliberately deferred — the former only pays off once something is actually scraping it (a hosting/observability-stack decision not yet made), the latter once a CI pipeline exists to stamp a git SHA into the build.
- Test suite (`tests/`) covers all of the above — verified non-vacuous multiple times by temporarily reintroducing bugs (lazy-load, route-ordering) and confirming the matching test fails. Standing conventions going forward: (1) every new feature gets both a unit test (pure logic, no DB/HTTP) where there's unit-testable logic to cover, and a regression test (real endpoint, real Postgres) — not just whichever is more convenient; (2) write clean code that avoids the kind of issues SonarQube/Checkmarx flag (injection, missing input validation at boundaries, unbounded queries, mass assignment, path traversal, sensitive data in logs, etc.) as a standing bar, not just when explicitly asked to review.
- Also done: rate limiting via **slowapi** (`app/rate_limit.py`) — a global `default_limits=["200/minute"]` safety net on every route, with tighter overrides on the two endpoints that actually needed them: `POST /auth/login` (`5/minute`, slows single-IP credential stuffing without affecting a real user who mistypes a password) and `POST /users/` signup (`10/hour`, prevents mass account creation / email-enumeration via the "already registered" signal). Keyed by client IP, in-memory storage — correct for one app instance, but each instance counts independently once there's more than one behind a load balancer, quietly raising the real effective limit; the fix then is `Limiter(storage_uri=...)` pointed at Redis, a one-file change in `app/rate_limit.py`, not an application-wide one. `tests/conftest.py` resets the limiter's in-memory counters before every test (`app.state.limiter.reset()`) so one test's requests never count against another's limit.
- Also done: CI (`.github/workflows/ci.yml`) — two independent jobs on every push/PR: `test` (spins up the same `postgis/postgis:16-3.4` image as `docker-compose.yml`, runs `alembic upgrade head` to verify migrations apply cleanly, then the full test suite) and `dependency-audit` (`pip-audit` against the exact pins in `requirements.txt`). Separate jobs so a new CVE disclosure on an existing pin shows up as its own failing check rather than being buried in (or blocking) the test run.
- Also done: a real dependency-CVE remediation pass, not just adding the audit job — see CLAUDE.md's gotcha entry for the specifics (what got bumped, and why `python-jose` was replaced outright rather than re-pinned). `pip-audit -r requirements.txt` is clean as of this pass; it will not stay that way forever, which is the entire point of running it in CI rather than once.
- Also done: router split — `providers.py` and `bookings.py` had each grown to cover multiple distinct concerns in one file (profile+search+availability+portfolio; bookings+reviews+messages). Split into one router module per concern, same URL prefixes, zero behavior change (verified: route table before/after is identical, full suite passes unchanged): `providers.py` (profile CRUD + search only), `provider_availability.py`, `portfolio.py` (all three `prefix="/providers"`); `bookings.py` (booking lifecycle only), `messages.py` (`prefix="/bookings"`). `reviews.py` is the one exception — review creation (`POST /bookings/{booking_id}/review`) and listing (`GET /providers/{profile_id}/reviews`) are one DOMAIN concern split across two URL prefixes, so that router has no `prefix=` at all and each route spells out its full path; grouping by concept beat forcing it into whichever prefix-based file happened to be more convenient. Two shared pieces came out of this: `app/booking_access.py` (`authorize_booking_party`, `get_owning_provider_profile` — a plain module both `bookings.py` and `messages.py` depend on, not one router importing from another) and `get_current_provider_profile` in `app/security.py` (a third link in the `get_current_user` → `get_current_provider` dependency chain, resolving "my own ProviderProfile row" — used by `provider_availability.py` and `portfolio.py` so neither hand-rolls that lookup).
- Also done: API versioning — every endpoint now lives under `/v1` (URL-path versioning, chosen over header-based versioning as the simplest scheme for a mobile client and the standard choice for this kind of API), assembled in one place: `app/routers/v1.py` builds a parent `APIRouter(prefix="/v1")` and `include_router()`s every feature router into it, and `app/main.py` includes just that one aggregator. Done now, before any real client exists, specifically because a mobile app installed on real phones can't be force-updated the way a web frontend can be redeployed — a breaking change with no versioning would strand whoever hasn't updated. `/health` and `/health/ready` are deliberately NOT under `/v1` (infrastructure/load-balancer endpoints, not the API contract), and neither is `/media` (static file serving). `OAuth2PasswordBearer(tokenUrl=...)` in `app/security.py` had to be updated to `/v1/auth/login` too — easy to miss, since it only breaks the `/docs` Swagger UI's "Authorize" button, not anything a test would normally catch. **Note for future reference**: path examples in bullets above this one were written before this change and show pre-`/v1` paths (e.g. `POST /auth/login`) — mentally prepend `/v1` to any endpoint path mentioned earlier in this file; this bullet and everything after it use the current, correct `/v1/...` form.
- Also done: pre-launch cost mitigation pass (three code-level levers that don't depend on a hosting decision). (1) **Photo compression on upload** — `app/storage.py`'s `_compress_image` (new `Pillow` dependency) resizes to a 1600px-longest-edge cap and re-encodes as JPEG at quality 85, regardless of upload format — a typical phone photo is far higher resolution than any screen displays it at, and every stored byte is a storage cost now and a bandwidth cost on every future view. On-disk extension for every photo is always `.jpg` post-compression, overriding whatever `ALLOWED_CONTENT_TYPES` said for the original format. Side effect, not the main point: uploads are now actually decoded, not just trusted by declared `Content-Type` — a spoofed/corrupt "image" gets a clean 400 instead of being written to disk as an unopenable file. Video is NOT transcoded (would need ffmpeg + async/background processing, separate work). (2) **`Cache-Control: public, max-age=31536000, immutable`** on `/media` responses (new middleware in `app/main.py`) — filenames are server-generated UUIDs that never change content, so this is a pure win: most repeat views never hit the server again. (3) **`GZipMiddleware`** on API responses — cuts bandwidth egress on JSON listings for free; Starlette's default `exclude_content_types` already skips image/video types, so it doesn't waste CPU re-compressing `/media`.
- **Gotcha hit while adding GZipMiddleware**: `app.add_middleware()` builds a LIFO stack (most-recently-added ends up OUTERMOST). `GZipMiddleware`'s `minimum_size` check silently breaks — it compresses EVERY response regardless of size — if the layer directly beneath it (its immediate inner neighbor in the stack) is itself `BaseHTTPMiddleware`-based, which `SlowAPIMiddleware` (and FastAPI's own `@app.middleware("http")` decorator) is. Confirmed empirically with a minimal repro, not just reasoned about — see `tests/regression/test_response_compression.py`. Fix: add `GZipMiddleware` BEFORE `SlowAPIMiddleware` (and before any `@app.middleware("http")` decorator), so it wraps the router directly with nothing `BaseHTTPMiddleware`-shaped in between. If a new middleware is ever added to `app/main.py`, check which side of `GZipMiddleware` it lands on.
- **Gotcha**: `settings.media_root` is read once, at app-startup, to construct the `/media` `StaticFiles` mount — monkeypatching the *setting* in a test doesn't retroactively change that already-constructed instance. Worse, `StaticFiles` serves from `self.all_directories` (a list computed once from `directory` at `__init__`), not `self.directory` itself — patching `directory` alone still 404s. A test that needs to actually fetch an uploaded file via its `/media/...` URL (not just check the file exists on disk) must patch both attributes on the route's `.app` — see the `_use_tmp_media_root` fixture in `tests/regression/test_portfolio.py`.
- **Security fix found and closed while building ID verification (pre-existing, not introduced that session)**: `POST /v1/users/` is public/unauthenticated and `UserCreate.role` accepted any `UserRole` including `admin` with zero restriction — anyone could self-register a fully-privileged admin account. Fixed with a `field_validator` on `UserCreate.role` (`app/schemas/user.py`) rejecting `admin` at signup. **There is now no API path that grants the admin role at all.** Admin accounts are provisioned by the operator directly: `UPDATE users SET role = 'admin' WHERE email = '...';` against the real DB, after a normal signup as customer/provider. This is deliberate, not a stopgap — a solo-operator app doesn't need a "promote to admin" API surface, and building one would just be more attack surface to secure for no real benefit at this scale.
- Also done: ID verification — `IdentityVerification` model (one row per user, unique `user_id`; a resubmission REPLACES the row rather than appending history — see the model's docstring for why), `get_current_admin` added to `app/security.py`'s dependency chain (same pattern as `get_current_provider`). Two new routers: `verification.py` (self-service — `POST /v1/verification/me` submit/resubmit, `GET /v1/verification/me` check own status, `GET /v1/verification/me/document` view own upload) and `admin.py` (review — `GET /v1/admin/verifications?status=` list/filter, `GET /v1/admin/verifications/{id}/document` view anyone's document, `PATCH /v1/admin/verifications/{id}` approve/reject, reject requires a `rejection_reason`). Resubmission is blocked once `approved` (409) but allowed from `pending` or `rejected`; reviewing an already-reviewed (non-pending) row is blocked (400) — one admin decision sticks, it doesn't get silently overwritten by a second PATCH. **Storage is deliberately separate from portfolio media** (`app/verification_storage.py`, not `app/storage.py`): a different root directory (`settings.verification_root`) never mounted as a public `StaticFiles` route anywhere (unlike `/media`), and no resize/recompress — a government ID needs to stay legible for the one admin who'll ever look at it, unlike a portfolio photo viewed repeatedly by many browsing customers where bandwidth cost matters. Documents are streamed back via `Response(..., headers={"Cache-Control": "no-store"})` from an authenticated endpoint, never handed back as a URL. **Gotcha hit writing the reject-requires-reason validation**: a `field_validator` on `rejection_reason` using `info.data` to check the sibling `status` field never fired when `rejection_reason` was omitted — Pydantic v2 skips field validators for a field left at its default unless `validate_default=True` is set on it. Fixed by using one `model_validator(mode="after")` instead (same pattern already used elsewhere for cross-field checks — see `ProviderAvailabilityUpdate`'s overlap check — this is the second time that pattern was the right call, worth defaulting to it for any new cross-field validation rather than reaching for `field_validator` + `info.data` first).
- Also done: reporting/flagging. **First draft scoped `Report` to target a `ProviderProfile` only — wrong, caught by the user mid-build** ("why can only providers get reported? what about users"): the roadmap's safety narrative is explicitly two-way (customers visit providers' homes/shops now; providers may travel to customers' homes in V2), so misbehavior can come from either side. Corrected: `Report.reported_user_id` targets a `User` (either role) — a report against a provider just uses their `User.id` (already exposed as `ProviderProfilePublic.user_id`), not their `ProviderProfile.id`. `app/routers/reports.py` (`POST /v1/users/{user_id}/report`, any authenticated user, any `ReportReason`, self-reports rejected with 400) and `app/routers/admin.py` extended with `GET /v1/admin/reports?status=`, `PATCH /v1/admin/reports/{id}` (resolve/dismiss; re-reviewing an already-decided report is blocked, same pattern as verification review).
- **Two independent, intentionally uncoupled deactivation levers** came out of the reporting redesign — picking the right one (or both) is an admin judgment call per report, not something the system forces: (1) `ProviderProfile.is_active` (`PATCH /v1/admin/providers/{profile_id}/status`) — hides just the business listing from `GET /providers/search` (an added `is_active = true` filter; no new index needed, the existing GiST spatial index already drives that query) and blocks new bookings (`create_booking` returns 404, not 400/403 — deliberately the same response a nonexistent profile would give, so a moderated provider isn't told "you're flagged" by the booking error itself) — but the account stays fully usable (login, messaging, existing bookings) and the profile stays visible via direct `GET /{profile_id}` (existing bookings/reviews/portfolio reference it by FK). (2) `User.is_active` (`PATCH /v1/admin/users/{user_id}/status`) — the harsher lever, works for either role: rejects login (`/v1/auth/login` returns 403) AND rejects every subsequent request on an already-issued token (`get_current_user` in `app/security.py` checks it too — a token issued before deactivation must stop working immediately, not linger until it expires). Deactivating a provider's account **cascades** to deactivating their `ProviderProfile` too (an account suspension should never leave a bookable profile behind) — reactivating does **not** cascade back (resuming account access and trusting the business profile again are different decisions; the safer default requires the profile to be explicitly re-enabled separately). Neither lever requires resolving any report, and resolving a report doesn't require either lever — all independent.
- Also done: a requested gap-analysis pass across the whole codebase (prompted by the reporting bug above — "are there other gaps like that one"), fixing everything confirmed as a real gap rather than an intentional tradeoff:
  - **Self-booking/self-review loophole closed**: `create_booking` (`app/routers/bookings.py`) now rejects `provider_profile.user_id == current_user.id` with 400 — previously a provider could book their own profile, complete it, and leave themselves a fake review (nothing in `create_review` would have caught it, since it only checks `booking.customer_id == current_user.id`, trivially true for a self-booking).
  - **`Booking.price`/`transport_fee` now reject negative values** (`Field(ge=0)` in `app/schemas/booking.py`) — previously fully client-controlled with zero bounds; matters more once Stripe lands but the trust boundary was already wrong.
  - **Email is now case-normalized** (`UserCreate.email` lowercases in `app/schemas/user.py`; `/v1/auth/login` lowercases `form_data.username` too, since that's a raw OAuth2 form field that bypasses the schema validator) — previously `User@x.com`/`user@x.com` registered as two accounts and a user could get a false "incorrect password" by typing their own email in different case than they signed up with.
  - **`GET /v1/users/{id}` now requires auth and returns a reduced `UserSummary` (no email, no `is_active`) for anyone except yourself or an admin** (new schema + updated router in `app/schemas/user.py`/`app/routers/users.py`) — previously fully public/unauthenticated, returning a stranger's email and moderation status to anyone who had or guessed a UUID, for no reason anything else in the app depended on.
  - **Tighter rate limits added to two more abuse-prone endpoints**, matching the pattern already used for login/signup: `POST /providers/me/portfolio` (`20/hour` — otherwise one compromised account could write up to the 25MB cap × 200 times/minute under the generic default, directly undoing the cost-mitigation work from earlier this session) and `POST /users/{id}/report` (`10/hour` — otherwise mass-reporting a single target 200 times/minute is itself a harassment vector).
  - **Admins can no longer review their own stuff or deactivate themselves**: `review_verification`/`review_report` (`app/routers/admin.py`) reject reviewing a submission/report that's about the reviewing admin (400); `set_user_active_status` rejects an admin deactivating their own account (400). Low-severity given the "no API grants admin, only a direct DB update" trust model, but confirmed rather than left undecided.
  - **Confirmed as intended, not an oversight** (documented in `get_current_provider_profile`'s docstring in `app/security.py`): a provider whose `ProviderProfile.is_active` is `False` can still manage their own portfolio/availability — profile deactivation hides the listing and blocks new bookings, it was never meant to block self-management the way `User.is_active` blocks the whole account.
  - **Confirmed accurate scope, not a bug**: reviews stay customer→provider only (the roadmap only ever asks for "rate providers," never the reverse) — this looked like it could be the same asymmetry class as the reporting bug, but it isn't.
  - **Flagged, not fixed — needs a separate conversation**: no password reset, no email verification at signup, no JWT refresh token exist anywhere in the app (confirmed via grep, zero hits). Password reset specifically is the biggest gap on the list given this is going live in a few months — every real user will eventually forget their password, and right now only a direct DB edit by the operator can help them. Building it needs an email-sending service (SES/SendGrid/Postmark) — an external-account dependency like Stripe, not something to build blind.
- Also done: a requested OWASP Top 10 (2021) pass across the whole codebase, fixing the three concrete findings (most categories were already solid or already-flagged):
  - **Password strength**: `UserCreate.password` now requires `min_length=8` (`app/schemas/user.py`) — previously zero length/complexity requirement at all, a 1-character password was accepted. No complexity rules (no "must contain a symbol") — current NIST SP 800-63B guidance favors length over enforced complexity.
  - **Log injection (CWE-117) in the login path, closed**: `OAuth2PasswordRequestForm.username` (`app/routers/auth.py`) is a raw form field, never validated through `EmailStr` the way signup's email is — a crafted value containing `\n` could forge a fake extra line in a file-based log via the "Failed login attempt" warning. Fixed by filtering to `ch.isprintable()` before using the value anywhere (query AND log) — safe because nothing containing a control character could ever match a real stored (`EmailStr`-validated) email anyway, so this doesn't change matching behavior, only what reaches the log. - Also done: a first load test (`load_test/`), using **k6** (a single Homebrew-installed binary, no new Python dependency for a one-off diagnostic tool) against the real local stack (Docker Postgres, uvicorn — not a mock). `booking_flow.js` simulates a realistic, non-uniform traffic mix (mostly search/profile/review browsing, a slice of login, a smaller slice of the full booking write path) rather than hammering one endpoint. **Key constraint that shaped the setup**: the global rate limiter is keyed by client IP, and every k6 VU on one machine shares that IP — so a naive run just measures the rate limiter rejecting requests, not real app/DB capacity. Fixed properly, not hacked around: `Settings.rate_limit_default` (`app/config.py`) makes the global default configurable via an env var (`RATE_LIMIT_DEFAULT`, defaults to the existing `200/minute`, zero behavior change by default — confirmed via the full suite still passing unchanged), so a local load test run can raise it for itself without touching any code or weakening the real default. The two explicit per-route overrides (login `5/minute`, signup `10/hour`) are deliberately NOT raised by this — they're real anti-abuse limits being exercised as part of the test, not a thing to work around. **Bug caught and fixed in the test script itself, not the app**: the first run's `setup()` made 6 login calls (5 providers + 1 customer) against that fixed `5/minute` login limit, so the 6th came back 429 with no `access_token` — silently producing an `Authorization: Bearer undefined` header that 401'd on every subsequent request using it, which looked like a 100% failure rate on the booking-write path. Fixed by trimming `setup()` to exactly 5 logins and making a missing token fail loudly (`throw`) instead of silently poisoning the rest of the run. **Results** (20 concurrent VUs, 60s sustained, ~1900 iterations, local machine): search (PostGIS radius query + ratings subquery) p95 38ms, provider detail p95 22ms, reviews p95 28ms, full 4-request booking write flow p95 146ms, zero 5xx errors, 100% of checks passed. See `load_test/RESULTS.md` for the full writeup and caveats (this is a local smoke-level test, not a production capacity-planning one — no attempt made yet at the "millions of users" scale the scaling-posture decision explicitly deferred tuning for).
