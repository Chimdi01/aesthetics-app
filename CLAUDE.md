# Project context for Claude Code

## What this is
A multi-vertical beauty services marketplace (hair, makeup, beauty, skincare, nails, barbers — not barber-specific, despite folder history). Working name: "aesthetics-app" (final brand name not yet decided — candidate "Capy" is under consideration but unresolved due to naming collisions).

Two-sided marketplace: customers book providers (shop visit or house-call), pay for service + optional transport, rate providers, browse portfolios (photos/video) with an AR try-on feature planned (SDK-based, not built in-house). A separate, unrelated venture (home-cooked food delivery marketplace) is being built in parallel by the same person — different codebase, not part of this project.

## Stack
- **Backend:** Python, FastAPI, async SQLAlchemy 2.0, PostgreSQL + PostGIS (for future geospatial provider search), asyncpg driver
- **Local dev DB:** Docker Compose (`postgis/postgis:16-3.4` image)
- **Migrations:** Alembic (async-aware `alembic/env.py`, DB URL sourced from `app.config.settings` rather than duplicated in `alembic.ini`). App no longer calls `Base.metadata.create_all` at startup — run `alembic upgrade head` against a fresh DB instead.
- **Tests:** pytest + pytest-asyncio + httpx, in `tests/` (`tests/unit/` = no DB/HTTP; `tests/regression/` = full endpoint tests against a real Postgres DB via httpx's `ASGITransport`). Test-only deps live in `requirements-dev.txt` (`-r requirements.txt` + pytest/pytest-asyncio/httpx), not `requirements.txt`, so a production install doesn't pull in test tooling. Run with `venv/bin/python -m pytest`.
- **Planned:** React Native for mobile, Next.js for web, Stripe Connect for marketplace split payments

## Conventions established so far
- **Pydantic schemas are always separate from SQLAlchemy models** — schemas live in `app/schemas/`, models in `app/models/`. Never let a DB model (with fields like `hashed_password`) double as an API response shape.
- **UUID primary keys**, not auto-incrementing integers — avoids leaking sequential IDs publicly.
- **One `User` table with a `role` enum** (`customer` / `provider` / `admin`) rather than separate tables per role. Role-specific data (e.g. a future `ProviderProfile`) goes in its own related table, not bolted onto `User`.
- **`get_db` dependency injection pattern** for DB sessions in routes — don't manage session lifecycle manually in route functions.
- Passwords hashed with `passlib` (bcrypt), never stored or returned in plain text. Hashing/JWT logic is centralized in `app/security.py` (not duplicated per-router) — `get_current_user` and `get_current_provider` (a dependency built on top of another dependency) live there.
- **Never access a lazy-loaded SQLAlchemy relationship (e.g. `user.provider_profile`) after an `await db.get(...)` call returns** — it raises `MissingGreenlet` since the attribute access happens outside the async bridge. Query explicitly instead (`select(...).where(...)`).
- New/changed tables go through an Alembic migration (`alembic revision --autogenerate -m "..."`, then check the generated file before applying), not `create_all`.
- **Provider specialties are a `categories` array on `ProviderProfile`** (`ServiceCategory` enum: hair/makeup/nails/barber/skincare; Postgres `ARRAY(Enum)` column, min 1 required), not a separate provider-type/role concept. A provider who does more than one thing (e.g. hair + makeup) just has multiple entries in one list — deliberately chosen over a full per-service catalog (name/price/duration per offering) for now; revisit if/when Booking needs per-service pricing, since a category alone doesn't carry price or duration.
- **Adding a NOT NULL column via Alembic against a table that may already have rows**: autogenerate's plain `add_column(..., nullable=False)` will fail if any rows exist. Pattern used here (see `alembic/versions/d1a56813a16e_...py`): add nullable → backfill existing rows via `op.execute(...)` → `op.alter_column(..., nullable=False)`.
- **Alembic + Postgres ENUM columns added via `op.add_column` (not `op.create_table`)**: the ENUM type isn't auto-created the way it is during table creation — fails with `type "X" does not exist`. Fix: explicitly `postgresql.ENUM(...).create(op.get_bind(), checkfirst=True)` before `add_column`, and the mirror `.drop(...)` in `downgrade()`.
- **Reusing an existing Postgres ENUM type in a NEW `op.create_table`** (e.g. `bookings.category` reusing `servicecategory`, already created by `provider_profiles.categories`): `op.create_table` tries to `CREATE TYPE` for every enum column regardless of whether it already exists, unless told otherwise — fails with `type "X" already exists`. Fix: use `postgresql.ENUM(..., create_type=False)` explicitly for that column (generic `sa.Enum(..., create_type=False)` accepts the kwarg without error but does NOT actually suppress the `CREATE TYPE` — has to be the Postgres-specific class).
- **GeoAlchemy2 + Alembic**: autogenerate omits `import geoalchemy2` from the migration (NameError) and emits a redundant `create_index` for the Geography column (GeoAlchemy2 already creates the GiST index on `add_column`, so it fails with "already exists"). Add the import, delete the explicit index calls, and add `CREATE EXTENSION IF NOT EXISTS postgis` for fresh databases. Also: never chain `alembic downgrade` after an `upgrade` in one command — if the upgrade fails, the downgrade rolls back the *previous* migration.
- **FastAPI route registration order**: a path like `/{booking_id}` (typed `uuid.UUID`) still matches at the STRING level first — the UUID conversion happens only after a route already matched. A literal-path route (`/as-customer`) registered AFTER `/{booking_id}` never gets reached; a request to it matches `/{booking_id}` first, fails UUID conversion on the literal text, and returns 422. Static/literal routes must be registered before parameterized ones at the same path depth (see `app/routers/bookings.py`).
- **Every new FK/filter column gets an index in the same migration that adds it** — not retrofitted later. When a query both filters on a column and sorts by another (e.g. "messages for this booking, oldest first"), that's one composite index `(filter_col, sort_col)`, not two separate indexes — see `Message`, `Booking`, `Review`, `PortfolioMedia`, `ProviderAvailability` for the pattern. This is cheap to get right at column-creation time and materially more disruptive to add later against a table with real production rows (see the next entry).
- **Adding an index to a table that might already have real rows** (i.e. anything except a table being created in the same migration): use `op.create_index(..., postgresql_concurrently=True)`, wrapped in `with op.get_context().autocommit_block():` (`CONCURRENTLY` can't run inside a transaction, which is what a migration normally runs in). A plain `CREATE INDEX` takes a lock that blocks writes to that table for the build's duration — fine on an empty/dev table, a real incident on one with production traffic. See `alembic/versions/3b1f6c9d0aa1_add_indexes_for_scale.py`. A brand-new table created in the same migration (see `messages` in `2245f79fd675_add_messages_table.py`) doesn't need this — nothing can be writing to a table that doesn't exist yet.

## Known environment gotchas already hit (don't reintroduce)
- `pydantic[email]` extra is required for `EmailStr` fields — plain `pydantic` install alone throws `ImportError: email-validator is not installed`.
- `greenlet` must be an explicit dependency — SQLAlchemy's async engine fails at runtime (`ValueError: the greenlet library is required...`) without it, even though it's not always auto-installed as a transitive dependency.
- `passlib==1.7.4` is incompatible with `bcrypt>=4.0` — passlib's internal backend self-test crashes on *every* `hash()`/`verify()` call (`ValueError: password cannot be longer than 72 bytes`), not just long passwords. Fixed by pinning `bcrypt==3.2.2`.
- `OAuth2PasswordRequestForm` (used by `/auth/login`) needs `python-multipart` installed for FastAPI's form parsing, or the app fails at startup with `RuntimeError: Form data requires "python-multipart"`.
- Local Postgres port conflict: a native Homebrew `postgresql@14` service listens on `127.0.0.1:5432`/`[::1]:5432`. Since it's a more specific bind than Docker's `*:5432`, `localhost:5432` connections get routed to the Homebrew instance instead of the Docker container, which doesn't have the app's DB role — surfaces as `role "aesthetics_user" does not exist`. Fixed by moving Docker's Postgres to host port **5433** (see `docker-compose.yml` / `DATABASE_URL`) instead of touching the Homebrew service.
- Alembic autogenerate against this DB picks up every PostGIS extension table (`tiger`/`topology` schemas, `spatial_ref_sys`, ~70 tables) unless `alembic/env.py` sets `include_object` to skip reflected tables with no counterpart in our own `Base.metadata` — without it, autogenerate proposes dropping all of them. The filter itself lives in `app/alembic_support.py` (not inline in `env.py`), specifically so it's unit-testable — importing `alembic/env.py` directly runs a real migration as a side effect.
- Test DB engine (`tests/conftest.py`) must use `poolclass=NullPool` — tests run across multiple event loops (the session-setup fixture's own `asyncio.run()`, then pytest-asyncio's per-test loop), and asyncpg connections are bound to the loop that created them. A normal pool tries to reuse a connection across loops and raises `InterfaceError: cannot perform operation: another operation is in progress`. NullPool opens a fresh connection per checkout instead of caching one.
- The session-setup fixture in `tests/conftest.py` must `Base.metadata.drop_all` before `create_all` — `create_all` only creates tables that don't exist yet, it never alters an existing one. A test DB left over from before a model change (e.g. a new column) silently keeps its stale schema, and tests fail with "column ... does not exist" in a way that doesn't obviously point at "your test DB needs resetting".
- All of the above are already pinned/configured — if you touch dependencies, `alembic/env.py`, or `tests/conftest.py`, keep these in place.
- Run the app with `python -m uvicorn app.main:app --reload`, not bare `uvicorn ...` — on this machine the bare command was resolving to a different (non-venv) Python interpreter and causing false "module not found" errors.
- **Mocking the DB engine in a unit test**: `unittest.mock.patch("app.main.engine.connect", ...)` fails with `AttributeError: 'AsyncEngine' object attribute 'connect' is read-only` — SQLAlchemy's `AsyncEngine.connect` can't be patched as an instance attribute. Patch the whole module-level `engine` name instead (`patch("app.main.engine")`, then set `.connect.side_effect` on the resulting mock) — see `tests/unit/test_readiness_check.py`.
- **Dependency CVE remediation (first pass, prompted by adding `pip-audit` to CI)**: `python-jose==3.3.0` had an unfixed CVE (PYSEC-2025-185) and hard-depends on `ecdsa` (also unfixed, a timing side-channel in ECDSA *signing* — irrelevant to this app anyway, since `jwt_algorithm` is `HS256`, which never touches that code path). No version re-pin could fix either, so `python-jose` was replaced outright with **PyJWT** (`app/security.py`'s `from jose import JWTError, jwt` → `import jwt`; `JWTError` → `jwt.PyJWTError`; `jwt.encode`/`jwt.decode` call signatures are compatible, no other changes needed). Separately, `starlette` (pulled in transitively by `fastapi`) had several CVEs fixed only in the 1.x series — bisected to the *minimum* `fastapi` version that resolves to a clean `starlette` (`fastapi==0.134.0` → `starlette==1.7.0`) rather than jumping to the latest `fastapi` release, which pulls in an additional `opentelemetry-api` dependency unrelated to the fix and not worth the extra surface. `starlette`, `annotated-doc`, and `typing-inspection` (fastapi's other new transitive deps at this version) are pinned explicitly in `requirements.txt`, same reasoning as `greenlet` — a transitive dependency that matters enough to pin on its own rather than let float. Verified via the full test suite plus a manual smoke test of signup/login/JWT-auth/rate-limiting against a real running server, not just unit tests, specifically because this touched auth.

## Where things stand
- Done: project skeleton, DB connection, `User` model, `ProviderProfile` model (1:1 with `User`, `role=provider`), `UserCreate`/`UserPublic`/`ProviderProfileCreate`/`ProviderProfilePublic` schemas, `POST`/`GET` endpoints for both, JWT auth (`POST /auth/login`, `get_current_user`/`get_current_provider` dependencies protecting provider-profile creation), Alembic migrations (initial schema migration applied, `create_all` removed from app startup). Confirmed running locally end-to-end.
- Also done: `ProviderProfile.categories` (multi-select `ServiceCategory` array — see Conventions) so multi-specialty providers (e.g. hair + makeup) don't need special-casing. `Booking` model/schemas/router (`POST /bookings/`, `GET /bookings/{id}`, `GET /bookings/as-customer`, `GET /bookings/as-provider`, `PATCH /bookings/{id}/status`) — customer ↔ `ProviderProfile`, category (must be one the provider offers), shop-visit vs. house-call (address required for the latter), status state machine (`requested → confirmed → completed`, `cancelled` from either non-terminal state; confirm/complete are provider-only, cancel is either party). Price/transport_fee are optional nullable fields for now (no per-service pricing catalog yet — see the categories-vs-Service-model tradeoff noted above).
- Also done: `Review` model/schema/routes — `POST /bookings/{booking_id}/review` (customer-only, requires the booking to be `completed`, one review per booking — enforced by a unique constraint on `booking_id` plus an application-level check) and `GET /providers/{profile_id}/reviews` (public listing, newest first). `provider_profile_id` is denormalized onto `Review` (copied from the booking at creation time) so listing/aggregating a provider's reviews doesn't need a join through `Booking` — same tradeoff already made for `Booking.category`. Rating is constrained to 1–5 both in the Pydantic schema (`Field(ge=1, le=5)`, returns 422) and as a DB `CheckConstraint` (defense in depth, in case a row is ever inserted outside the API).
- Also done (security hardening pass on reviews): `ReviewCreate.comment` rejects embedded null bytes via a Pydantic `field_validator` — Postgres rejects `\x00` in text columns at the driver level, which would otherwise surface as an unhandled 500 instead of a clean 422. `GET /providers/{profile_id}/reviews` takes `limit` (default 20, max 100) / `offset` query params — an unbounded SELECT there would let a provider with a large review history turn every page load into an ever-growing query.
- Also done: portfolio photo/video upload — `PortfolioMedia` model, `POST /providers/me/portfolio` (multipart upload, provider-only), `GET /providers/{profile_id}/portfolio` (public, paginated), `DELETE /providers/me/portfolio/{media_id}` (owner-only). Storage is local disk for now (`app/storage.py`, path from `settings.media_root`, served via `StaticFiles` mounted at `/media` in `app/main.py`) — **explicitly a placeholder**: local disk doesn't survive a redeploy on most hosting platforms and won't scale past one server, so this gets swapped for S3 before a real launch (the person building this has confirmed that's the plan). Everything that knows *where* files physically live is isolated in `app/storage.py`; routers/models only ever see the relative path it returns, specifically so that swap later touches one file, not the model/schema/router layer. Security hardening already applied here since it was built with the "avoid Sonar/Checkmarx-flagged issues" standard in mind from the start: content-type allowlist (rejects anything not image/jpeg, image/png, image/webp, video/mp4, video/quicktime), on-disk filenames are always server-generated (never the client-supplied filename, to block path traversal), upload size is capped while streaming chunk-by-chunk rather than trusting `Content-Length`, and `delete_file` refuses to unlink anything outside `media_root` even though the path it receives is always self-generated (defense in depth).
- Also done: location-based provider search — `ProviderProfile.location` (PostGIS `Geography(POINT, 4326)` via the new **GeoAlchemy2** dependency, nullable — providers without a location just don't appear in search) and `address_type` (`shop`/`home`, required whenever a location is given, per the roadmap). `GET /providers/search?latitude&longitude&radius_km&category&limit&offset` (public; radius default 10 / max 50 km, results sorted by distance with an id tiebreaker, includes `average_rating`/`review_count` from a grouped reviews subquery). **Privacy decision:** neither the profile response nor search results expose exact coordinates — a home provider's coordinates are effectively their home address — only `address_type` and a distance rounded to 0.1 km. Revisit (e.g. a coarsened point) if a map view needs pins. The GiST spatial index is created by GeoAlchemy2 itself when the column is added (an explicit `create_index` in the migration is a duplicate and fails). Test DB setup now runs `CREATE EXTENSION IF NOT EXISTS postgis` in `tests/conftest.py`.
- Also done: provider availability/working hours — `ProviderAvailability` model (`day_of_week` + `start_time`/`end_time`, one row per shift), `PUT /providers/me/availability` (provider-only, **full-replacement** semantics — deletes the provider's existing week and inserts the new one in the same request, rather than a per-day PATCH, since "set my working hours" is naturally one coherent action) and `GET /providers/{profile_id}/availability` (public, sorted Monday-first then by start time). **Split shifts are supported** (e.g. 09:00-12:00 and 14:00-18:00 on the same day) — multiple rows per day are allowed, but overlapping ranges on the same day are rejected in `ProviderAvailabilityUpdate` (`app/schemas/provider_availability.py`), not the DB: a single-row `CheckConstraint` can enforce `end_time > start_time` but can't compare across rows, so cross-range overlap has to be an application-level check. Booking creation deliberately does **not** validate against this table — providers already manually accept/decline every request, so an odd-hours booking just gets declined rather than blocked at request time; revisit only if usage shows it's needed. Times are timezone-naive wall-clock (fine for a single-city London launch, would need revisiting for multi-timezone expansion).
- Also done: in-app messaging — `Message` model, `POST /bookings/{booking_id}/messages` and `GET /bookings/{booking_id}/messages` (both in `app/routers/bookings.py`, reusing the booking-ownership check, not a new router — messaging is scoped to a Booking's back-and-forth, not a general DM system between arbitrary users, per the roadmap's V1 wording). Either party (customer or provider on that booking) can read/send; `_authorize_booking_party()` was factored out of the previously-duplicated is_customer/is_provider check (now shared by `get_booking`, `update_booking_status`, and both message endpoints). **Push notifications are explicitly NOT built** — that needs a push provider (FCM/APNs) and device-token registration, an external-account decision like Stripe, deferred for the same reason (no account/credentials to wire up yet). This just persists/retrieves messages.
- **Scaling posture (prompted by an explicit "millions of users, high concurrency" requirement):** the stance taken is "build the cheap, hard-to-retrofit foundations now; defer the expensive, premature infrastructure until real traffic justifies it" — see the new Convention entry below and the gotcha on `CONCURRENTLY` migrations. Concretely added: composite indexes on every FK/filter column an existing query actually uses (see the Convention entry), `db_pool_size`/`db_max_overflow`/`db_pool_timeout` made configurable in `app/config.py` (defaults are dev-appropriate, NOT scaled up blindly — real tuning is a per-deployment exercise, see the comment there), and `pool_pre_ping=True` on the engine (detects a stale pooled connection before handing it to a request, cheap insurance that matters more as connection churn grows). **Deliberately NOT done yet** (would be premature optimization pre-launch, and contradicts this project's own scope-discipline conventions): caching layer (Redis), read replicas, message queues/background workers, sharding, a CDN, multi-region. These are real V-next concerns once there's actual traffic data to size them against — worth raising in the architecture/roadmap conversation as a distinct "scaling milestones" discussion (e.g. "add read replicas when X", "add a queue when Y") rather than building speculatively now.
- Also done: application-wide logging — `app/logging_config.py` (`configure_logging()`, called once at import time in `app/main.py`) sets up the root logger via `logging.config.dictConfig`; every module just does `logger = logging.getLogger(__name__)` and logs normally, no per-module handler setup. `LOG_LEVEL` env var controls the level (default INFO). A per-request correlation id (`app/request_context.py`'s `request_id_var`, a `contextvars.ContextVar` — not a plain global, since it must stay correct across concurrently in-flight requests on one event loop) is set by a middleware in `app/main.py`, injected into every log line via `RequestIdFilter`, and echoed back as an `X-Request-ID` response header (reusing a caller-supplied one if present, for tracing across future hops like a load balancer). **Log-level policy, chosen specifically to stay sane at real traffic volume** (this was an explicit ask: "millions of users... concerned about how much logging will be done once there's even a little traffic"): the request-logging middleware logs by *outcome*, not by path — successful requests (2xx/3xx) are DEBUG, not INFO, because meaningful business events (booking created, review posted, login, profile/availability/portfolio changes) already get a purpose-built INFO log with real context from whichever router handled them; a generic "METHOD /path -> 200" line for every single request (every search, every profile view, every health-check poll) would otherwise dominate production logs without adding information. 4xx -> WARNING and 5xx -> ERROR regardless of path, since errors are actionable regardless of volume. Unhandled exceptions are caught in the middleware and logged via `logger.exception` (full traceback + request id) before re-raising, so nothing fails silently with only whatever uvicorn prints to stderr. **Never logged, anywhere**: passwords, raw JWTs/Authorization headers, user-generated message/review body content (not even at DEBUG — only metadata like sender id), or exact search/location coordinates above DEBUG (a home provider's or searching customer's coordinates are effectively a home address).
- Also done: `GET /health` (liveness — no dependency checks, must stay cheap since an orchestrator restarts the *process* on repeated failures here, which doesn't help if the database is what's actually down) and `GET /health/ready` (readiness — pings Postgres via `SELECT 1`, returns 503 if unreachable; a load balancer/orchestrator should route traffic away from an instance that's alive-but-not-ready rather than let it serve errors). Both endpoints' own successful responses are DEBUG-level under the log policy above, same as any other 2xx. A `/metrics` (Prometheus-style) endpoint and a build/version endpoint were considered and deliberately deferred — the former only pays off once something is actually scraping it (a hosting/observability-stack decision not yet made), the latter once a CI pipeline exists to stamp a git SHA into the build.
- Test suite (`tests/`) covers all of the above — verified non-vacuous multiple times by temporarily reintroducing bugs (lazy-load, route-ordering) and confirming the matching test fails. Standing conventions going forward: (1) every new feature gets both a unit test (pure logic, no DB/HTTP) where there's unit-testable logic to cover, and a regression test (real endpoint, real Postgres) — not just whichever is more convenient; (2) write clean code that avoids the kind of issues SonarQube/Checkmarx flag (injection, missing input validation at boundaries, unbounded queries, mass assignment, path traversal, sensitive data in logs, etc.) as a standing bar, not just when explicitly asked to review.
- Also done: rate limiting via **slowapi** (`app/rate_limit.py`) — a global `default_limits=["200/minute"]` safety net on every route, with tighter overrides on the two endpoints that actually needed them: `POST /auth/login` (`5/minute`, slows single-IP credential stuffing without affecting a real user who mistypes a password) and `POST /users/` signup (`10/hour`, prevents mass account creation / email-enumeration via the "already registered" signal). Keyed by client IP, in-memory storage — correct for one app instance, but each instance counts independently once there's more than one behind a load balancer, quietly raising the real effective limit; the fix then is `Limiter(storage_uri=...)` pointed at Redis, a one-file change in `app/rate_limit.py`, not an application-wide one. `tests/conftest.py` resets the limiter's in-memory counters before every test (`app.state.limiter.reset()`) so one test's requests never count against another's limit.
- Also done: CI (`.github/workflows/ci.yml`) — two independent jobs on every push/PR: `test` (spins up the same `postgis/postgis:16-3.4` image as `docker-compose.yml`, runs `alembic upgrade head` to verify migrations apply cleanly, then the full test suite) and `dependency-audit` (`pip-audit` against the exact pins in `requirements.txt`). Separate jobs so a new CVE disclosure on an existing pin shows up as its own failing check rather than being buried in (or blocking) the test run.
- Also done: a real dependency-CVE remediation pass, not just adding the audit job — see the new gotcha entry below for the specifics (what got bumped, and why `python-jose` was replaced outright rather than re-pinned). `pip-audit -r requirements.txt` is clean as of this pass; it will not stay that way forever, which is the entire point of running it in CI rather than once.
- Also done: router split — `providers.py` and `bookings.py` had each grown to cover multiple distinct concerns in one file (profile+search+availability+portfolio; bookings+reviews+messages). Split into one router module per concern, same URL prefixes, zero behavior change (verified: route table before/after is identical, full suite passes unchanged): `providers.py` (profile CRUD + search only), `provider_availability.py`, `portfolio.py` (all three `prefix="/providers"`); `bookings.py` (booking lifecycle only), `messages.py` (`prefix="/bookings"`). `reviews.py` is the one exception — review creation (`POST /bookings/{booking_id}/review`) and listing (`GET /providers/{profile_id}/reviews`) are one DOMAIN concern split across two URL prefixes, so that router has no `prefix=` at all and each route spells out its full path; grouping by concept beat forcing it into whichever prefix-based file happened to be more convenient. Two shared pieces came out of this: `app/booking_access.py` (`authorize_booking_party`, `get_owning_provider_profile` — a plain module both `bookings.py` and `messages.py` depend on, not one router importing from another) and `get_current_provider_profile` in `app/security.py` (a third link in the `get_current_user` → `get_current_provider` dependency chain, resolving "my own ProviderProfile row" — used by `provider_availability.py` and `portfolio.py` so neither hand-rolls that lookup).
- Also done: API versioning — every endpoint now lives under `/v1` (URL-path versioning, chosen over header-based versioning as the simplest scheme for a mobile client and the standard choice for this kind of API), assembled in one place: `app/routers/v1.py` builds a parent `APIRouter(prefix="/v1")` and `include_router()`s every feature router into it, and `app/main.py` includes just that one aggregator. Done now, before any real client exists, specifically because a mobile app installed on real phones can't be force-updated the way a web frontend can be redeployed — a breaking change with no versioning would strand whoever hasn't updated. `/health` and `/health/ready` are deliberately NOT under `/v1` (infrastructure/load-balancer endpoints, not the API contract), and neither is `/media` (static file serving). `OAuth2PasswordBearer(tokenUrl=...)` in `app/security.py` had to be updated to `/v1/auth/login` too — easy to miss, since it only breaks the `/docs` Swagger UI's "Authorize" button, not anything a test would normally catch. **Note for future reference**: path examples in the "Also done" bullets above this one were written before this change and show pre-`/v1` paths (e.g. `POST /auth/login`) — mentally prepend `/v1` to any endpoint path mentioned earlier in this file; this bullet and everything after it use the current, correct `/v1/...` form.
- Also done: pre-launch cost mitigation pass (three code-level levers that don't depend on a hosting decision). (1) **Photo compression on upload** — `app/storage.py`'s `_compress_image` (new `Pillow` dependency) resizes to a 1600px-longest-edge cap and re-encodes as JPEG at quality 85, regardless of upload format — a typical phone photo is far higher resolution than any screen displays it at, and every stored byte is a storage cost now and a bandwidth cost on every future view. On-disk extension for every photo is always `.jpg` post-compression, overriding whatever `ALLOWED_CONTENT_TYPES` said for the original format. Side effect, not the main point: uploads are now actually decoded, not just trusted by declared `Content-Type` — a spoofed/corrupt "image" gets a clean 400 instead of being written to disk as an unopenable file. Video is NOT transcoded (would need ffmpeg + async/background processing, separate work). (2) **`Cache-Control: public, max-age=31536000, immutable`** on `/media` responses (new middleware in `app/main.py`) — filenames are server-generated UUIDs that never change content, so this is a pure win: most repeat views never hit the server again. (3) **`GZipMiddleware`** on API responses — cuts bandwidth egress on JSON listings for free; Starlette's default `exclude_content_types` already skips image/video types, so it doesn't waste CPU re-compressing `/media`.
- **Gotcha hit while adding GZipMiddleware**: `app.add_middleware()` builds a LIFO stack (most-recently-added ends up OUTERMOST). `GZipMiddleware`'s `minimum_size` check silently breaks — it compresses EVERY response regardless of size — if the layer directly beneath it (its immediate inner neighbor in the stack) is itself `BaseHTTPMiddleware`-based, which `SlowAPIMiddleware` (and FastAPI's own `@app.middleware("http")` decorator) is. Confirmed empirically with a minimal repro, not just reasoned about — see `tests/regression/test_response_compression.py`. Fix: add `GZipMiddleware` BEFORE `SlowAPIMiddleware` (and before any `@app.middleware("http")` decorator), so it wraps the router directly with nothing `BaseHTTPMiddleware`-shaped in between. If a new middleware is ever added to `app/main.py`, check which side of `GZipMiddleware` it lands on.
- **Gotcha**: `settings.media_root` is read once, at app-startup, to construct the `/media` `StaticFiles` mount — monkeypatching the *setting* in a test doesn't retroactively change that already-constructed instance. Worse, `StaticFiles` serves from `self.all_directories` (a list computed once from `directory` at `__init__`), not `self.directory` itself — patching `directory` alone still 404s. A test that needs to actually fetch an uploaded file via its `/media/...` URL (not just check the file exists on disk) must patch both attributes on the route's `.app` — see the `_use_tmp_media_root` fixture in `tests/regression/test_portfolio.py`.
- Not yet done: Stripe integration, AR feature, mobile/web frontends, push notifications, ID verification, provider-side calendar sync (Google Calendar/iCal — the roadmap pairs this with availability, but it's a separate, larger workstream not built yet), metrics/observability beyond logs. Portfolio media storage is on local disk, not S3 — flagged above as a known placeholder to revisit. A thumbnail-vs-full-size two-tier media system (separate compressed sizes for grid vs. detail view) was considered and deferred — the current single-compressed-version approach captures most of the cost win without a schema change; revisit if finer control is ever needed.

## How to work with the person on this
They're a backend developer (more comfortable with Python than with FastAPI specifically, and stronger in Spring/Java than Python's ecosystem overall) who explicitly wants to **understand the code, not just receive finished output**. Prefer building incrementally, explaining non-obvious choices (especially FastAPI/SQLAlchemy-specific patterns they may not have hit in other stacks) as you go, rather than generating large amounts of code silently. When you make a structural decision (new model, new pattern, new dependency), it's worth a line explaining why, not just what.

They also work with a separate Claude conversation for overall architecture/business/legal/roadmap planning — if a change here has implications beyond this codebase (e.g., a scope or timeline shift), it's worth flagging to them explicitly so they can raise it there rather than assuming it's fully decided.
