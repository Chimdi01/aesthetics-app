# Project context for Claude Code

## What this is
A multi-vertical beauty services marketplace (hair, makeup, beauty, skincare, nails, barbers — not barber-specific, despite folder history). Working name: "aesthetics-app" (final brand name not yet decided — candidate "Capy" is under consideration but unresolved due to naming collisions).

Two-sided marketplace: customers book providers (shop visit or house-call), pay for service + optional transport, rate providers, browse portfolios (photos/video) with an AR try-on feature planned (SDK-based, not built in-house). A separate, unrelated venture (home-cooked food delivery marketplace) is being built in parallel by the same person — different codebase, not part of this project.

## Stack
- **Backend:** Python, FastAPI, async SQLAlchemy 2.0, PostgreSQL + PostGIS (for future geospatial provider search), asyncpg driver
- **Local dev DB:** Docker Compose (`postgis/postgis:16-3.4` image)
- **Migrations:** Alembic (async-aware `alembic/env.py`, DB URL sourced from `app.config.settings` rather than duplicated in `alembic.ini`). App no longer calls `Base.metadata.create_all` at startup — run `alembic upgrade head` against a fresh DB instead.
- **Tests:** pytest + pytest-asyncio + httpx, in `tests/` (`tests/unit/` = no DB/HTTP; `tests/regression/` = full endpoint tests against a real Postgres DB via httpx's `ASGITransport`). Test-only deps live in `requirements-dev.txt` (`-r requirements.txt` + pytest/pytest-asyncio/httpx), not `requirements.txt`, so a production install doesn't pull in test tooling. Run with `venv/bin/python -m pytest`.
- **Lint/type-check:** ruff (lint) + mypy (type-check), both in `requirements-dev.txt`, configured in `pyproject.toml`, enforced in CI's `lint` job. See `CHANGELOG.md` for what's configured and why (ignored rules, line-length choice, etc.).
- **Secrets-scanning:** gitleaks, run against full commit history in CI's `secrets-scan` job (not a Python dependency — installed from the upstream release binary in the workflow itself). See `CHANGELOG.md` for why it's the plain binary, not the marketplace action.
- **Secrets rotation:** see `SECRETS_ROTATION.md` — what each secret protects, routine vs. emergency rotation steps, and the multi-key JWT verification support (`JWT_PREVIOUS_SECRET_KEYS`) built specifically so rotating `JWT_SECRET_KEY` doesn't instantly break every active session.
- **Load testing:** k6 (`load_test/`, Homebrew binary, not a Python dependency), against the real local Docker Postgres + uvicorn stack. Run `k6 run load_test/booking_flow.js` — see `load_test/README.md` for setup (including why `RATE_LIMIT_DEFAULT` needs raising for a meaningful local run) and `load_test/RESULTS.md` for the latest numbers.
- **Planned:** React Native for mobile, Next.js for web, Stripe Connect for marketplace split payments

## Conventions established so far
- **Pydantic schemas are always separate from SQLAlchemy models** — schemas live in `app/schemas/`, models in `app/models/`. Never let a DB model (with fields like `hashed_password`) double as an API response shape.
- **UUID primary keys**, not auto-incrementing integers — avoids leaking sequential IDs publicly.
- **One `User` table with a `role` enum** (`customer` / `provider` / `admin`) rather than separate tables per role. Role-specific data (e.g. a future `ProviderProfile`) goes in its own related table, not bolted onto `User`.
- **`get_db` dependency injection pattern** for DB sessions in routes — don't manage session lifecycle manually in route functions.
- Passwords hashed with `passlib` (bcrypt), never stored or returned in plain text. Hashing/JWT logic is centralized in `app/security.py` (not duplicated per-router) — `get_current_user` and `get_current_provider` (a dependency built on top of another dependency) live there.
- **Never access a lazy-loaded SQLAlchemy relationship (e.g. `user.provider_profile`) after an `await db.get(...)` call returns** — it raises `MissingGreenlet` since the attribute access happens outside the async bridge. Query explicitly instead (`select(...).where(...)`).
- New/changed tables go through an Alembic migration (`alembic revision --autogenerate -m "..."`, then check the generated file before applying), not `create_all`.
- **Provider specialties are a `categories` array on `ProviderProfile`** (`ServiceCategory` enum: hair/makeup/nails/barber/skincare; Postgres `ARRAY(Enum)` column, min 1 required), not a separate provider-type/role concept. A provider who does more than one thing (e.g. hair + makeup) just has multiple entries in one list — deliberately chosen over a full per-service catalog (name/price/duration per offering) for now; revisit if/when Booking needs per-service pricing, since a category alone doesn't carry price or duration.
- **Adding a NOT NULL column via Alembic against a table that may already have rows**: autogenerate's plain `add_column(..., nullable=False)` will fail if any rows exist. Pattern used here (see `alembic/versions/d1a56813a16e_...py`): add nullable → backfill existing rows via `op.execute(...)` → `op.alter_column(..., nullable=False)`.
- **Alembic + Postgres ENUM columns added via `op.add_column` (not `op.create_table`)**: the ENUM type isn't auto-created the way it is during table creation — fails with `type "X" does not exist`. Fix: explicitly `postgresql.ENUM(...).create(op.get_bind(), checkfirst=True)` before `add_column`, and the mirror `.drop(...)` in `downgrade()`.
- **Reusing an existing Postgres ENUM type in a NEW `op.create_table`** (e.g. `bookings.category` reusing `servicecategory`, already created by `provider_profiles.categories`): `op.create_table` tries to `CREATE TYPE` for every enum column regardless of whether it already exists, unless told otherwise — fails with `type "X" already exists`. Fix: use `postgresql.ENUM(..., create_type=False)` explicitly for that column (generic `sa.Enum(..., create_type=False)` accepts the kwarg without error but does NOT actually suppress the `CREATE TYPE` — has to be the Postgres-specific class).
- **GeoAlchemy2 + Alembic**: autogenerate omits `import geoalchemy2` from the migration (NameError) and emits a redundant `create_index` for the Geography column (GeoAlchemy2 already creates the GiST index on `add_column`, so it fails with "already exists"). Add the import, delete the explicit index calls, and add `CREATE EXTENSION IF NOT EXISTS postgis` for fresh databases. Also: never chain `alembic downgrade` after an `upgrade` in one command — if the upgrade fails, the downgrade rolls back the *previous* migration.
- **FastAPI route registration order**: a path like `/{booking_id}` (typed `uuid.UUID`) still matches at the STRING level first — the UUID conversion happens only after a route already matched. A literal-path route (`/as-customer`) registered AFTER `/{booking_id}` never gets reached; a request to it matches `/{booking_id}` first, fails UUID conversion on the literal text, and returns 422. Static/literal routes must be registered before parameterized ones at the same path depth (see `app/routers/bookings.py`).
- **Every new FK/filter column gets an index in the same migration that adds it** — not retrofitted later. When a query both filters on a column and sorts by another (e.g. "messages for this booking, oldest first"), that's one composite index `(filter_col, sort_col)`, not two separate indexes — see `Message`, `Booking`, `Review`, `PortfolioMedia`, `ProviderAvailability` for the pattern. This is cheap to get right at column-creation time and materially more disruptive to add later against a table with real production rows (see the next entry).
- **Adding an index to a table that might already have real rows** (i.e. anything except a table being created in the same migration): use `op.create_index(..., postgresql_concurrently=True)`, wrapped in `with op.get_context().autocommit_block():` (`CONCURRENTLY` can't run inside a transaction, which is what a migration normally runs in). A plain `CREATE INDEX` takes a lock that blocks writes to that table for the build's duration — fine on an empty/dev table, a real incident on one with production traffic. See `alembic/versions/3b1f6c9d0aa1_add_indexes_for_scale.py`. A brand-new table created in the same migration (see `messages` in `2245f79fd675_add_messages_table.py`) doesn't need this — nothing can be writing to a table that doesn't exist yet.
- **Cross-model SQLAlchemy forward references**: when model A relates to model B and B relates back to A (e.g. `User` ↔ `ProviderProfile`), importing either at the top of the other's module is a real circular import. Use a string annotation (`Mapped["ProviderProfile | None"]`) for the relationship itself, AND add `if TYPE_CHECKING: from app.models.provider_profile import ProviderProfile` near the top of the other module — the string resolves at runtime via SQLAlchemy's own mapper registry, while the `TYPE_CHECKING` import resolves the name for mypy and ruff's F821 at lint/type-check time with zero runtime cost (the import never actually executes). Use this pattern for any new cross-model relationship rather than a bare string annotation plus a `# noqa: F821`.
- **Any DB-backed, single-use/revocable opaque secret token** (refresh tokens, email verification, password reset) goes through `app/secret_tokens.py`'s `generate_raw_token()` + `hash_token()` pair, never a JWT — a JWT's whole point is being stateless/self-contained, which is the opposite of what a revocable-before-expiry token needs (see that module's docstring). Only the hash is ever stored; the raw value exists only transiently in the response/email handed to the client once.
- **Helper modules that mutate an `AsyncSession` (`app/refresh_tokens.py`, `app/email_tokens.py`, `app/booking_access.py`) never call `db.commit()` themselves** — they stage changes (`add`/`update`), and the calling router commits once. Keeps one obvious place per request where a transaction actually ends, rather than each helper owning its own boundary.
- **A security control that changes behavior based on account/credential state (lockout, "this email isn't registered", etc.) must not change the HTTP RESPONSE in a way that reveals that state** — see `app/login_lockout.py`: a locked-out login attempt gets the exact same generic 401 a wrong password gets (same anti-enumeration stance as `/auth/forgot-password`'s generic response and login's email case-normalization). Distinguish the cases in server-side logs only, never in what the caller gets back. Where practical, also keep response TIMING similar between branches (see `login()`'s locked-out path still calling `verify_password` and discarding the result) — a response that's reliably faster/slower is itself a side channel, even with an identical body.

## Known environment gotchas already hit (don't reintroduce)
- `pydantic[email]` extra is required for `EmailStr` fields — plain `pydantic` install alone throws `ImportError: email-validator is not installed`.
- `greenlet` must be an explicit dependency — SQLAlchemy's async engine fails at runtime (`ValueError: the greenlet library is required...`) without it, even though it's not always auto-installed as a transitive dependency.
- `passlib==1.7.4` is incompatible with `bcrypt>=4.0` — passlib's internal backend self-test crashes on *every* `hash()`/`verify()` call (`ValueError: password cannot be longer than 72 bytes`), not just long passwords. Fixed by pinning `bcrypt==3.2.2`.
- `OAuth2PasswordRequestForm` (used by `/auth/login`) needs `python-multipart` installed for FastAPI's form parsing, or the app fails at startup with `RuntimeError: Form data requires "python-multipart"`.
- Local Postgres port conflict: a native Homebrew `postgresql@14` service listens on `127.0.0.1:5432`/`[::1]:5432`. Since it's a more specific bind than Docker's `*:5432`, `localhost:5432` connections get routed to the Homebrew instance instead of the Docker container, which doesn't have the app's DB role — surfaces as `role "aesthetics_user" does not exist`. Fixed by moving Docker's Postgres to host port **5433** (see `docker-compose.yml` / `DATABASE_URL`) instead of touching the Homebrew service.
- Alembic autogenerate against this DB picks up every PostGIS extension table (`tiger`/`topology` schemas, `spatial_ref_sys`, ~70 tables) unless `alembic/env.py` sets `include_object` to skip reflected tables with no counterpart in our own `Base.metadata` — without it, autogenerate proposes dropping all of them. The filter itself lives in `app/alembic_support.py` (not inline in `env.py`), specifically so it's unit-testable — importing `alembic/env.py` directly runs a real migration as a side effect.
- Test DB engine (`tests/conftest.py`) must use `poolclass=NullPool` — tests run across multiple event loops (the session-setup fixture's own `asyncio.run()`, then pytest-asyncio's per-test loop), and asyncpg connections are bound to the loop that created them. A normal pool tries to reuse a connection across loops and raises `InterfaceError: cannot perform operation: another operation is in progress`. NullPool opens a fresh connection per checkout instead of caching one.
- The session-setup fixture in `tests/conftest.py` must `Base.metadata.drop_all` before `create_all` — `create_all` only creates tables that don't exist yet, it never alters an existing one. A test DB left over from before a model change (e.g. a new column) silently keeps its stale schema, and tests fail with "column ... does not exist" in a way that doesn't obviously point at "your test DB needs resetting".
- All of the above are already pinned/configured — if you touch dependencies, `alembic/env.py`, or `tests/conftest.py`, keep these in place.
- Run the app with `python -m uvicorn app.main:app --reload`, not bare `uvicorn ...` — on this machine the bare command was resolving to a different (non-venv) Python interpreter and causing false "module not found" errors.
- **Mocking the DB engine in a unit test**: `unittest.mock.patch("app.main.engine.connect", ...)` fails with `AttributeError: 'AsyncEngine' object attribute 'connect' is read-only` — SQLAlchemy's `AsyncEngine.connect` can't be patched as an instance attribute. Patch the whole module-level `engine` name instead (`patch("app.main.engine")`, then set `.connect.side_effect` on the resulting mock) — see `tests/unit/test_readiness_check.py`.
- **Cross-field Pydantic validation: use `model_validator(mode="after")`, not `field_validator` + `info.data`.** A `field_validator` on field B that reads sibling field A via `info.data` silently never runs when B is left at its default (Pydantic v2 skips validators for defaulted fields unless `validate_default=True`) — exactly the case that matters for something like "B is required when A == X" if the caller omits B entirely. Actually hit this bug in `VerificationReviewUpdate`'s first draft (reject-requires-reason, caught by its own test) before switching to `model_validator`; `ProviderAvailabilityUpdate`'s overlap check already used `model_validator` from the start and never had the problem. Default to `model_validator` for any new cross-field check.
- **Dependency CVE remediation (first pass, prompted by adding `pip-audit` to CI)**: `python-jose==3.3.0` had an unfixed CVE (PYSEC-2025-185) and hard-depends on `ecdsa` (also unfixed, a timing side-channel in ECDSA *signing* — irrelevant to this app anyway, since `jwt_algorithm` is `HS256`, which never touches that code path). No version re-pin could fix either, so `python-jose` was replaced outright with **PyJWT** (`app/security.py`'s `from jose import JWTError, jwt` → `import jwt`; `JWTError` → `jwt.PyJWTError`; `jwt.encode`/`jwt.decode` call signatures are compatible, no other changes needed). Separately, `starlette` (pulled in transitively by `fastapi`) had several CVEs fixed only in the 1.x series — bisected to the *minimum* `fastapi` version that resolves to a clean `starlette` (`fastapi==0.134.0` → `starlette==1.7.0`) rather than jumping to the latest `fastapi` release, which pulls in an additional `opentelemetry-api` dependency unrelated to the fix and not worth the extra surface. `starlette`, `annotated-doc`, and `typing-inspection` (fastapi's other new transitive deps at this version) are pinned explicitly in `requirements.txt`, same reasoning as `greenlet` — a transitive dependency that matters enough to pin on its own rather than let float. Verified via the full test suite plus a manual smoke test of signup/login/JWT-auth/rate-limiting against a real running server, not just unit tests, specifically because this touched auth.
- **Creating two new, FK-related rows in the same commit when the ORM classes have no `relationship()` between them** (just a raw FK column — e.g. a brand-new `User` plus a brand-new `EmailToken` referencing its `user_id`, with no `relationship()` configured either way): SQLAlchemy's flush does NOT reliably order the inserts by the underlying tables' FK constraint in this case — hit this as a real `ForeignKeyViolationError` (`email_tokens` insert attempted before the `users` insert), not reasoned about in advance. Fix: `await db.flush()` right after `db.add()`-ing the parent object and before constructing/adding the row that references its id — see `app/routers/users.py`'s `create_user`. Not needed when the referenced row already exists from an earlier, already-committed request (e.g. issuing a refresh token for an existing user at login) — only when both rows are new in the same flush.

## Where things stand
Full build history with rationale lives in **`CHANGELOG.md`** — this
section is just the current-state summary, kept short on purpose so it
doesn't drift back into a second copy of that file.

**Built:** auth (JWT access + refresh tokens with rotation, multi-key JWT verification for secret rotation, per-account login lockout on top of per-IP rate limiting, `get_current_user`/`get_current_provider`/`get_current_admin` dependency chain, email verification, password reset) · `User` + `ProviderProfile` (multi-category) · provider search (PostGIS radius search) · provider availability/working hours · bookings (full lifecycle + state machine) · in-app messaging (scoped to a booking) · reviews · portfolio photo/video upload (local disk, see below) · ID verification (self-service submit + admin review) · reporting/flagging (either role, two independent deactivation levers) · admin moderation surface · rate limiting · structured logging with request-id correlation · health/readiness endpoints · `/v1` API versioning · CI (`test`, `lint`, `secrets-scan`, `dependency-audit` — see `.github/workflows/ci.yml`) · a completed OWASP Top 10 pass, a completed cross-cutting gap-analysis pass, and a completed dependency-CVE remediation pass.

**Known, deliberate placeholders (not oversights):**
- Portfolio media storage is local disk (`app/storage.py`), not S3 — will not survive a redeploy or scale past one server; swap is planned before real launch and isolated to that one file.
- Email sending (`app/email.py`) only has a "console" backend (logs the email instead of sending it) — no SES/SendGrid/Postmark account exists yet, same external-account reasoning as Stripe. Verification/reset links work end-to-end in dev/test (the link lands in the log); swapping in a real provider is isolated to this one file.
- `email_verified` is tracked on `User` but NOT enforced anywhere (login, bookings, etc. all work regardless) — whether/where to gate on it is a product decision, flagged rather than assumed.
- No caching layer, read replicas, queues, CDN, or multi-region — deferred until real traffic data justifies them (see CHANGELOG's "Scaling posture" entry).
- No Content-Security-Policy, no CORS config — both deferred until a web frontend actually exists to tune them against.
- No secrets vault (AWS Secrets Manager, Vault) — secrets are plain env vars; `SECRETS_ROTATION.md` documents manual rotation. No platform-wide "revoke every refresh token for every user" admin action either — only per-user (`logout-all`); flagged in that runbook as a gap for a severe-enough incident, not built.
- No account-level 2FA/MFA, no admin-action audit trail beyond the generic request logs.

**Not yet done:** Stripe integration, AR feature, mobile/web frontends, push notifications, provider-side calendar sync, metrics/observability beyond logs, extending reporting to cover reviews/messages (not just users), a real email-provider integration (see placeholder above).

## How to work with the person on this
They're a backend developer (more comfortable with Python than with FastAPI specifically, and stronger in Spring/Java than Python's ecosystem overall) who explicitly wants to **understand the code, not just receive finished output**. Prefer building incrementally, explaining non-obvious choices (especially FastAPI/SQLAlchemy-specific patterns they may not have hit in other stacks) as you go, rather than generating large amounts of code silently. When you make a structural decision (new model, new pattern, new dependency), it's worth a line explaining why, not just what.

They also work with a separate Claude conversation for overall architecture/business/legal/roadmap planning — if a change here has implications beyond this codebase (e.g., a scope or timeline shift), it's worth flagging to them explicitly so they can raise it there rather than assuming it's fully decided.
